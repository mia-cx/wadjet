# Recording and GIF pipeline on macOS 26

Research for [#3](https://github.com/mia-cx/wadjet/issues/3), checked 2026-10-07. Target is macOS 26+. Mia currently uses macOS 27 and Xcode 27 beta.

## Short answer and recommendation

Use `SCStream` with `SCRecordingOutput` for the first implementation. Apple provides direct recording of screen, system audio, and microphone to a file. Add the output before starting, handle start/failure/finish delegates, and release the finished Capture to its Workflow only after the finish event. These APIs predate macOS 26. [Apple recording API](https://developer.apple.com/documentation/screencapturekit/screcordingoutput), [WWDC24 recording example](https://developer.apple.com/videos/play/wwdc2024/10088/?time=578)

Recommend SDR H.264 MP4, 30 fps, aspect-preserving output capped at 1920 pixels on the longest edge. Make native resolution and 60 fps explicit Workflow choices. Record GIF Workflows to a temporary video first, then decode, resize, and encode after finalization. Start with native ImageIO. Consider gifski when a measured quality improvement justifies its dependency and licensing. These are proposed product defaults, not performance measurements. [Stream configuration](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration), [ImageIO destinations](https://developer.apple.com/documentation/imageio/cgimagedestination), [gifski C API](https://github.com/ImageOptim/gifski/blob/61ac230f65374c70f238cb35f9247cd22b4672f1/gifski.h)

iShare already uses this recording API. Its source has finalization races, missing recording-event handling, and a GIF deadlock. Avoiding those defects matters more than replacing ScreenCaptureKit. We cannot establish Mia's exact historical failure without her installed version, settings, and logs. No app was launched and no permission prompt was triggered during this research. [iShare recording engine](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Capture/CaptureEngine.swift), [GIF pipeline](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Capture/VideoCapture.swift)

## Recording API choice

| Choice | What it gives wadjet | Recommendation |
| --- | --- | --- |
| `SCStream` + `SCRecordingOutput` | Framework-managed encoding and file writing; selectable file type and video codec; recording events, duration and byte count. | Default for ordinary MP4 Recording. |
| `SCStream` + `AVAssetWriter` | App-managed tracks, compression settings, sample timestamps and custom processing. | Add only for a concrete requirement the direct output cannot meet. |

Sources for the comparison: [recording configuration](https://developer.apple.com/documentation/screencapturekit/screcordingoutputconfiguration), [recording output](https://developer.apple.com/documentation/screencapturekit/screcordingoutput), [AVAssetWriter](https://developer.apple.com/documentation/avfoundation/avassetwriter), [Apple reader/writer guide](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/AVFoundationPG/Articles/05_Export.html).

`SCRecordingOutputConfiguration` exposes codec and container selection, but no public bitrate, compression-quality, or maximum-file-size setting in the inspected SDK. Query `availableVideoCodecTypes` and `availableOutputFileTypes`; do not treat a codec/container pair as supported solely because the enums exist. A hard Destination byte limit needs post-processing or a custom writer. Monitoring `recordedFileSize` is useful for stopping, but is not a guarantee about final muxed size. [Configuration](https://developer.apple.com/documentation/screencapturekit/screcordingoutputconfiguration), [recordedFileSize](https://developer.apple.com/documentation/screencapturekit/screcordingoutput/recordedfilesize), [SDK evidence below](#sdk-evidence)

With `AVAssetWriter`, the app owns session timing, input readiness, append failures, and completion. Use one serialized writer owner; accept complete video frames; use source presentation timestamps; keep bounded queues. Finish inputs and await `finishWriting`, then check status and error. Fixed encoder dimensions require scaling or padding resized windows into the original canvas. This is an implementation recommendation derived from Apple's writer lifecycle and stream metadata. [Writer guide](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/AVFoundationPG/Articles/05_Export.html), [finishWriting](https://developer.apple.com/documentation/avfoundation/avassetwriter/finishwriting(completionhandler:)), [frame metadata](https://developer.apple.com/documentation/screencapturekit/scstreamframeinfo)

## Region, window, and screen

Use a display filter for full-screen Recording, a display filter plus `sourceRect` for a region, and `SCContentFilter(desktopIndependentWindow:)` for one window. `sourceRect` uses points in the display's logical coordinate system. Output width/height use pixels. Translate Freeze Frame selection to the selected display's coordinates, then scale with that display/filter's pixel scale. Never assume every display shares `NSScreen.main`'s scale. [Content filters](https://developer.apple.com/documentation/screencapturekit/sccontentfilter), [sourceRect](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/sourcerect), [pointPixelScale](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/pointpixelscale), [SDK evidence below](#sdk-evidence)

Keep one output canvas for each Recording. Define how window resizing fits into it before implementing dynamic reconfiguration. Recommend scaling with preserved aspect ratio and padding; start a new file if the user changes the capture source. These are product choices. ScreenCaptureKit can update live filters and configurations, but that capability does not establish seamless encoder size changes. [Apple capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [iShare resize report](https://github.com/itoolio/ishare/issues/69)

Apple's system picker grants access to the selected content without requiring broad Screen Recording permission. A custom Freeze Frame selection path needs its own permission handling. Do not preflight broad enumeration and label every failure "permission denied" before opening a picker that can authorize its own selection. [WWDC23 picker and consent](https://developer.apple.com/videos/play/wwdc2023/10136/), [shareable content](https://developer.apple.com/documentation/screencapturekit/scshareablecontent)

For v1, constrain region selection to one display. Cross-display regions need a separate decision about scale, coordinate conversion, and composition. This is a scope recommendation based on the display-specific filter and source rectangle. [sourceRect](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/sourcerect)

## Cursor, clicks, audio, and HDR

- `showsCursor` renders the cursor into the stream. `showMouseClicks` draws click circles and is independent of cursor visibility. The inspected Apple header restricts click rendering to BGRA. Set BGRA explicitly when clicks are enabled; test the encoded file. Native circles avoid a custom event-monitoring overlay for v1. [Cursor](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/showscursor), [clicks](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/showmouseclicks), [SDK evidence below](#sdk-evidence)
- `capturesAudio` captures system/app audio subject to the content filter. `excludesCurrentProcessAudio` can exclude wadjet's own sounds. Microphone uses `captureMicrophone` and an optional `AVCaptureDevice.uniqueID` through `microphoneCaptureDeviceID`. System audio needs no virtual audio driver. [Audio configuration](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration), [WWDC24 microphone example](https://developer.apple.com/videos/play/wwdc2024/10088/?time=485), [WWDC22 filtering](https://developer.apple.com/videos/play/wwdc2022/10155/)
- Microphone authorization is separate. Include the exact `NSMicrophoneUsageDescription` key, check authorization, and request only when the user enables microphone capture. A sandboxed build also needs the audio-input entitlement. Verify the built bundle, not just the source plist. [Apple authorization guide](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media), [usage description](https://developer.apple.com/documentation/bundleresources/information-property-list/nsmicrophoneusagedescription)
- macOS 27 adds `mixesAudioWithMicrophone`. Its default is true; false retains separate system and microphone tracks. Availability-gate it. The new control does not prove the exact macOS 26 track layout or mixing behavior. Verify system-only, mic-only, and both on macOS 26 before promising editable tracks or specific playback behavior. [Apple mixing documentation](https://developer.apple.com/documentation/screencapturekit/screcordingoutputconfiguration/mixesaudiowithmicrophone)
- macOS 26 adds `.captureHDRRecordingPreservedSDRHDR10`, a dedicated HDR10 recording preset. Distinguish it from macOS 15's HDR **stream** presets. The SDK still contains an older warning that adding recording output to an HDR stream fails, despite defining the newer recording preset. Recommend SDR for v1; prototype the dedicated preset separately with HEVC and playback/color checks. Do not infer that arbitrary HDR stream configurations record correctly. [HDR recording preset](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/preset/capturehdrrecordingpreservedsdrhdr10), [SDK evidence below](#sdk-evidence)

## Frame rate, resolution, and resource use

`minimumFrameInterval = CMTime(value: 1, timescale: 30)` caps requested updates at 30 fps. It does not force a new frame every 1/30 second. Preserve timing when the screen is static, including the final held frame. Apple's sample checks `.complete` frame status and uses a queue depth of five. More queued surfaces consume more memory; Apple says not to exceed eight. Set queue depth explicitly because Apple's older sample and current SDK disagree about its default. [WWDC22 stream tuning](https://developer.apple.com/videos/play/wwdc2022/10155/), [capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [minimumFrameInterval](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/minimumframeinterval), [queueDepth](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/queuedepth)

At 1920×1080, one BGRA frame holds about 8.3 MB. Five surfaces hold about 41.5 MB before encoder and other overhead. At 3840×2160, those figures quadruple. These are width × height × four-byte calculations, not measured resident memory. A 60 fps ceiling doubles the maximum frame count compared with 30 fps. That does not imply twice the encoded file size. [Pixel formats and frame queue](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration)

For GIF, propose a 960-pixel longest edge, 10 fps for ImageIO initially, and a 15-second default limit. If higher frame rates are needed, use unclamped delays and validate playback timing. These are starting points for a benchmark, not established quality or size results. Compare scrolling text, gradients, click circles, and static holds at 640/960/1280 pixels and 10/15/20 fps. Record encode time, peak memory, bytes, readability, and playback duration. [GIF timing](https://developer.apple.com/documentation/imageio/kcgimagepropertygifdelaytime), [unclamped timing](https://developer.apple.com/documentation/imageio/kcgimagepropertygifunclampeddelaytime), [gifski API](https://github.com/ImageOptim/gifski/blob/61ac230f65374c70f238cb35f9247cd22b4672f1/gifski.h)

## GIF encoding

ImageIO is the smallest dependency choice. Create a GIF destination, add ordered frames and GIF timing/loop properties, then check `CGImageDestinationFinalize`. `kCGImagePropertyGIFDelayTime` clamps delays below 100 ms; use `kCGImagePropertyGIFUnclampedDelayTime` when requesting faster animation, and test target viewers. Do not assume generic lossy-quality settings offer gifski-style palette optimization. [Image destinations guide](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/ImageIOGuide/ikpg_dest/ikpg_dest.html), [delay](https://developer.apple.com/documentation/imageio/kcgimagepropertygifdelaytime), [unclamped delay](https://developer.apple.com/documentation/imageio/kcgimagepropertygifunclampeddelaytime), [finalize](https://developer.apple.com/documentation/imageio/cgimagedestinationfinalize(_:))

gifski uses cross-frame palettes and temporal dithering. It provides a C library, so Swift can feed decoded pixels without shipping ffmpeg or PNG intermediates. Quality 90 is the library's recommendation; its fast option trades quality for encoding speed. Actual superiority for wadjet's UI recordings remains unmeasured. [gifski README](https://github.com/ImageOptim/gifski/blob/61ac230f65374c70f238cb35f9247cd22b4672f1/README.md), [C header](https://github.com/ImageOptim/gifski/blob/61ac230f65374c70f238cb35f9247cd22b4672f1/gifski.h)

Run gifski outside the main actor. Frame submission and `gifski_finish` can block. Supply consecutive frame indices, monotonic timestamps, sRGB unpremultiplied RGBA, and a file output before submitting frames. Finish on success, error, and cancellation; check the returned status. Its progress callback supports cancellation. These requirements come from its C header. [C API contract](https://github.com/ImageOptim/gifski/blob/61ac230f65374c70f238cb35f9247cd22b4672f1/gifski.h)

gifski offers AGPL or alternative commercial licensing. Resolve distribution terms before embedding it in a closed-source product; the repository being private does not settle that question. Keep the ImageIO path until this decision is made. [License](https://github.com/ImageOptim/gifski/blob/61ac230f65374c70f238cb35f9247cd22b4672f1/LICENSE), [vendor licensing](https://gif.ski/license.html)

Recommended GIF pipeline: finalized temporary MP4 → ordered decoded frames → resize/color conversion → encoder → verified GIF → After-Capture Steps → optional Destination. Use bounded decoding and retain the source video until conversion succeeds. This keeps encoding pressure away from the live stream. `AVAssetReader` can supply sequential samples; `AVAssetImageGenerator` can extract sampled times and apply track transforms. Handle zero-frame recordings, cancellation, and decode failures explicitly. [Asset reader](https://developer.apple.com/documentation/avfoundation/avassetreader), [image generator](https://developer.apple.com/documentation/avfoundation/avassetimagegenerator), [gifski blocking contract](https://github.com/ImageOptim/gifski/blob/61ac230f65374c70f238cb35f9247cd22b4672f1/gifski.h)

## Why iShare Recording fails

`castdrian/ishare` redirects to `itoolio/ishare`. I inspected current commit `deb7abcdfdef251647c532924bad38426a18b1b2` and latest published release `v4.2.6`, commit `ea732927236e88c2636f163335d27cc185d2e8fb`. The five inspected recording/picker/plist files have no differences between those revisions. The following are source findings, not a reproduction on Mia's machine. [Repository](https://github.com/castdrian/ishare), [release](https://github.com/itoolio/ishare/releases/tag/v4.2.6)

1. **It publishes an unfinished file.** `CaptureEngine.stopCapture` calls `stream?.stopCapture()` without a completion handler, clears the stream, and immediately returns `.success(url)`. After-recording work can race MP4 finalization. The class declares `SCRecordingOutputDelegate` but implements none of its recording callbacks. Apple's finish callback is the file-ready boundary. This explains a plausible missing-thumbnail/upload failure path. [Engine lines 99–129](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Capture/CaptureEngine.swift#L99-L129), [Apple finish event](https://developer.apple.com/documentation/screencapturekit/screcordingoutputdelegate/recordingoutputdidfinishrecording(_:))
2. **It loses asynchronous start/write failures.** `stream?.startCapture()` supplies no completion handler. The surrounding `do/catch` catches setup errors, not later start errors. Recording-output failure callbacks are absent. `isRunning` becomes true before selection/start succeeds, while later errors mostly print to the console. The UI can therefore report Recording without a successful recorder. [Engine](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Capture/CaptureEngine.swift#L51-L107), [ScreenRecorder](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Capture/ScreenRecorder.swift), [Apple start](https://developer.apple.com/documentation/screencapturekit/scstream/startcapture(completionhandler:))
3. **Its GIF post-processing deadlocks the main actor.** `postRecordingTasks` is `@MainActor`. It creates an inheriting `Task`, then calls `DispatchSemaphore.wait()` before that task can run. The task cannot reach `signal()` while its actor is blocked. This is a code-level deadlock path, independent of encoder quality. The exporter also has no callback to resume its continuation when the requested frame list is empty. [VideoCapture lines 54–85 and 143–208](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Capture/VideoCapture.swift#L54-L85), [Swift Task actor inheritance](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0304-structured-concurrency.md#context-inheritance)
4. **Microphone metadata and GIF timing are wrong.** Its plist key contains `NSMicrophoneUsageDescription` twice with embedded newlines, rather than the required exact key. No replacement build-setting key appears in the project file. This is a microphone authorization/crash risk; verify the built release before asserting its runtime outcome. Its GIF exporter requests 30 fps but writes the clamped delay key, conflicting with Apple's 100 ms minimum. [Plist](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Info.plist#L46-L50), [project settings](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare.xcodeproj/project.pbxproj), [required microphone key](https://developer.apple.com/documentation/bundleresources/information-property-list/nsmicrophoneusagedescription), [GIF exporter](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Capture/VideoCapture.swift#L153-L180), [Apple delay behavior](https://developer.apple.com/documentation/imageio/kcgimagepropertygifdelaytime)
5. **Picker and HDR handling add failure paths.** `canRecord` requires broad shareable-content enumeration before presenting the authorizing picker and treats all errors as permission denial. Picker setup configures a dummy stream, presents without that stream, then creates another stream and ignores the callback's stream. This is a lifecycle concern, not a proven universal cause. HDR mode selects the old canonical HDR stream preset and adds recording output; it does not use macOS 26's dedicated recording preset. [ScreenRecorder](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Capture/ScreenRecorder.swift), [picker manager](https://github.com/itoolio/ishare/blob/ea732927236e88c2636f163335d27cc185d2e8fb/ishare/Capture/ContentSharingPickerManager.swift), [Apple picker session](https://developer.apple.com/videos/play/wwdc2023/10136/), [HDR preset](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/preset/capturehdrrecordingpreservedsdrhdr10)

The issue history supports several distinct symptoms. #101 reports missing permission despite an enabled setting, then a crash after selection. #123 reports missing full-screen thumbnails on 4.2.1. #69 reports invalid MP4 after window resizing. #111 reports black bars; PR #124 later fixes scaling. These tickets are closed, so their reports do not establish current unresolved runtime defects. #142 requests region Recording. #72 confirms the move away from MovieRecorder. Do not diagnose current iShare as still using its old writer. [#101](https://github.com/itoolio/ishare/issues/101), [#123](https://github.com/itoolio/ishare/issues/123), [#69](https://github.com/itoolio/ishare/issues/69), [#111](https://github.com/itoolio/ishare/issues/111), [#124](https://github.com/itoolio/ishare/pull/124), [#142](https://github.com/itoolio/ishare/issues/142), [#72](https://github.com/itoolio/ishare/issues/72)

## Open risks and follow-up work

The API choice is supported by primary sources. Reliability on macOS 26 and Mia's macOS 27 beta is not measured here. The following should become an implementation-validation ticket, with licensing tracked separately if gifski is chosen.

1. Validate delegate-driven start/stop/failure handling on macOS 26 and 27. Include rapid stop, cancel before selection, permission denial/revocation, destination write failure, and repeated Recording. After-Capture Steps must never read an unfinished file. [Apple recording lifecycle](https://developer.apple.com/videos/play/wwdc2024/10088/?time=627)
2. Validate all four audio combinations, device changes, playback tracks, and A/V sync. Keep macOS 27's mixing setting availability-gated. [Audio mixing](https://developer.apple.com/documentation/screencapturekit/screcordingoutputconfiguration/mixesaudiowithmicrophone)
3. Validate Retina/non-Retina and multiple displays, region coordinate conversion, window resize/close, static holds, and native stop controls. Measure memory and dropped frames at the proposed defaults. [Stream configuration](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration), [frame status](https://developer.apple.com/documentation/screencapturekit/scframestatus)
4. Benchmark ImageIO versus gifski on representative clips before committing to a dependency. Resolve gifski licensing before distribution. Retain the temporary video on conversion failure. [ImageIO](https://developer.apple.com/documentation/imageio/cgimagedestination), [gifski license](https://gif.ski/license.html)
5. For [#10 Recording UX](https://github.com/mia-cx/wadjet/issues/10), decide resize behavior, audio scope, MP4/GIF limits, and what happens while GIF conversion runs. Show Recording only after confirmed start; distinguish stopping from file-ready and encoding. A hard upload size limit requires a separate encoding policy. These are recommendations derived from the recording lifecycle and exposed configuration, not settled UX decisions. [Lifecycle](https://developer.apple.com/documentation/screencapturekit/screcordingoutputdelegate), [configuration](https://developer.apple.com/documentation/screencapturekit/screcordingoutputconfiguration)
